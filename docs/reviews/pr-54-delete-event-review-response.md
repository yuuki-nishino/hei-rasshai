対象：[pr-54-delete-event-review.md](./pr-54-delete-event-review.md)。ルールは、devにデプロイ済み。devの実機の確認（テスト用のイベントの削除）は、問題なし。

| # | 判断 | 内容 | 反映先 |
|---|---|---|---|
| D1 | **未確認のまま、マージする（運用で確認）** | 本番のルールの上限（1回の書き込みで評価できる `get()` の回数）は、Emulator では分からない。同じ文書への `get()` は、まとめて数えられるはずで、1バッチ（450件）あたり、イベントとメンバーの2文書だけ。ただし、devで確かめるまでは、断言しない。**450件を超える注文のイベントを、devで削除して確かめる**。通らなければ（「削除できませんでした」）、`DELETE_BATCH` を下げる。**devの実機の確認は数十件で、バッチが1つしか動いていないため、D1 は確かめていない。手で600件を入れる手間が大きく、通らなくても削除が失敗するだけでデータは壊れないため、未確認のままマージする（ユーザーの判断）。大きなイベントを初めて消すときに確かめ、通らなければ `DELETE_BATCH` を下げる** | testing.md §5 |
| D2 | **見送り** | 画面は、イベントの購読をつないだままではなく、一覧の取得時のイベント情報を使っている。イベント本体が消えても、`DeleteStatus` は消えない。devの実機で、削除の最後に一覧へ自然に戻ることを確認した | — |
