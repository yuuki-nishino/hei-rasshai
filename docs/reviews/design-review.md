## 🔴 高：SPEC違反、またはデータ不整合につながるもの

### H1. 「やめる」の前の16秒待ちでは、遅れて登録される注文を防げない
対象：`design/order-confirm.md` §4.3（89行目）

16秒待ちは「SDKのトランザクションは15秒を超えて再試行しない」という前提に立っています。しかし、この前提は成り立ちません。

- JS SDKの `runTransaction` は、時間ではなく**試行回数**（既定5回）と指数バックオフで制限されます。`unavailable` も再試行の対象です。
- すでに送ったコミットのRPCが、弱い電波で16秒より後にサーバーへ届くこともあり得ます。

この場合、確認の時点では「存在しない」と判定して破棄し、その後に注文が登録されます。SPEC 5の「やめた後に、見えない注文ができてはいけない」に違反します。★C1として検証を予定していますが、Emulatorでは再現しにくく、検証で安全を示すのは難しいです。

**提案（墓標方式）**：時間に頼らず、Firestoreの原子性で排他にします。

- 「やめる」では、トランザクションで `orders/{orderId}` が無いことを確かめてから `voids/{orderId}` を作る
- 注文作成のルールに `!exists(.../voids/$(orderId))`、`voids` 作成のルールに `!exists(.../orders/$(orderId))` を入れる
- どちらか先にコミットした方が勝つので、待ち時間が要らなくなり、★C1は解消する
- 保留中の注文の復元（§4.4）で「登録されていませんでした」と判定するときも、同じく `void` を書く

### H2. `pendingOrder` のキーが1つしかないため、未確認の注文が追跡できなくなる
対象：`design/order-confirm.md` §2（22行目）、`design/screens.md` §1.3（44行目）

「確認できない」を閉じた後に次の注文を確定すると、`hei:pending:{eventId}` が上書きされます。前の注文は、登録されたかどうか分からないまま追跡が切れます。

**対策**：

- 未解決の注文がある間は確定を止めるか、配列で保持する
- `pendingOrder` は**トランザクションを始める前に**保存することを明記する
- 「登録されていませんでした」の表示には、入力し直せるよう `draft` の品目も出す

### H3. QRなしの注文は、支払い方法を変更できない
対象：`design/screens.md` §3.5（100〜103行目）

QRなしの注文は、確定した時点で `done` になります。ところが「支払い変更」のボタンは、調理中とできあがりのカードにしかありません。済みの表示中も、お渡し済み・取り消しのカードにはありません。注文の大半を占めるその場渡しの注文で、取り違えを直せないことになります。SPEC 4.3、6.2、8（確定後に支払い方法を変更でき、集計に反映される）を満たしません。

**対策**：お渡し済み・取り消しのカードにも「支払い変更」を付ける。売上画面に注文一覧を足して、そこから変更できるようにしてもよい。

### H4. 「未送信◯件」に、「渡した」「取り消し」が数えられない
対象：`design/data-access.md` §6（152・156行目）、§5（141行目）

ローカルの書き込みは、すぐにクエリの結果へ反映されます。そのため、`ready→done` や `→cancelled` の未送信の書き込みがある注文は、購読範囲（`status in [preparing, ready]`）から**すぐに外れます**。オフラインで最も多い操作（渡した）が、件数に出ません。

さらに §5 では、調理の購読を続けるのが「注文タブを開いている間」だけです。売上・メニューなどのタブでは、接続状態を判定できません（SPEC 6「常時表示」）。

**対策**：

- 書き込みのPromiseを、アプリ側で数える（書き込みで+1、解決・拒否で-1）
- 調理の購読は、`Shell` のレベルで常に続ける

### H5. お客様画面で、オフラインの「存在しない」を「注文が見つかりません」と誤って表示する
対象：`design/screens.md` §4.1（152行目）

メモリキャッシュでオフラインのとき、SDKは `exists()=false, fromCache=true` のスナップショットを返すことがあります。これをそのまま notFound として扱うと、電波が弱いだけのお客様に「見つかりません」と出てしまいます。

**対策**：`!exists && !metadata.fromCache` のときだけ notFound にする。`fromCache` で存在しないときは、loading（または通信エラー）の表示にする。

### H6. `watchMyEvents` が、自分の `members` を誤って削除するおそれがある
対象：`design/data-access.md` §3.2（51行目）

「取得できないイベント（削除済み・**権限なし**）は除外し、孤立した `members` は削除する」とあります。`permission-denied` や、一時的な `unavailable`、キャッシュからの読み取りが空だった場合にも削除が走ると、自分でイベントから抜けたことになり、元に戻せません。

**対策**：削除してよいのは、`getDocFromServer` で**存在しないことが確定した**ときだけ、と限定する。メンバーであれば、イベントが無くても `get` はルール上許可され、`exists()=false` が返る。

### H7. カートの価格の扱いが、同じ文書の中で矛盾している
対象：`design/screens.md` §3.4（76・77・88行目）

- 77行目は「`total` は**現在のメニューの価格**」
- 88行目は「**カートに入れた時点の**名前・価格で書き写す」

途中で価格が変わると、画面の合計と、保存される `items` の金額が食い違います。76行目の `cart: Map<menuId, qty>` も、88行目の方針と合いません。

**対策**：カートに入れた時点の値に統一する。売り切れになった品がカートに残っているときの扱いも決める。

### M10. オフラインの操作が拒否されても、再読み込みの後は通知できない

## 🧪 テスト計画の不足

### ルールのテストに足すもの
R1〜R7を、テストケースに対応付けることも含みます。

- メンバーが自分の `role` を `owner` に変える更新 → 拒否（**`members` の更新のテストが無い**）
- 注文の作成で、余計な項目（メールなど）、`payment: 'card'`、`number: 0`、`total < 0`、`items` が0行や51行 → 拒否
- 同じ状態のままの更新で、`cancelledFrom` を書き換える
- 招待を削除しない参加（S1）、`expiresAt` が1日を超える招待（S2）、カウンターの改ざん（S4）、`email` を偽ったメンバーの作成（S5）、オーナーが自分の `members` を削除（S6）
- 未知のサブコレクション（`events/{e}/foo/x`）への書き込み、`where` の無いコレクショングループの一覧 → 拒否

### 結合・単体のテストに足すもの

#### N1. 「確認できない」状態から、弱い電波のときに自動で抜けられない
対象：`design/order-confirm.md` §4（51・65行目）、§5.3

自動で確認し直すきっかけは、「起動時」と `online` イベントだけ。電波が弱いだけの状況では、`navigator.onLine` は `true` のままなので、`online` イベントは発火しない。そのため、「やめる」が8秒でタイムアウトして「確認できない」になると、**`pending` が残ったまま、確定ボタンが無効になり続ける**（レジが止まる）。

**対策（決定：自動＋手動）**：
- 接続状態の判定（`connectionStatus`）がオンラインに戻ったとき（`fromCache` の解消）に、自動で確認する
- 15秒ごとに、自動で再試行する
- 「もう一度確認」ボタンを出す

#### N2. 「やめる」の途中でアプリが落ちると、復元したときに誤った案内が出る
対象：`design/order-confirm.md` §5.2（117行目）、§5.3（121〜124行目）

`abandoning = true` を保存するのは、「確認できない」になったときだけ。墓標の書き込みが届いた直後に、`pending` を消す前にアプリが落ちると、次のようになる。
1. 起動時の確認で、注文が無い → 「前の注文は登録されていません」の画面（decide）になる
2. 「もう一度確定する」を押すと、墓標があるので `permission-denied` になる
3. 「登録できません。イベントのメンバーか確認してください」と出る（原因と違う案内）

**対策**：
- `abandoning = true` は、`voidOrFind` を**始める前に**保存する
- 起動時の確認では、注文と一緒に `voids/{orderId}` も確認する。墓標があれば、「やめた」として扱う
- `confirmOrder` が `permission-denied` になったときは、墓標の有無を確かめて、案内を分ける

#### N3. オフラインで起動すると、イベント一覧が空になる
対象：`design/data-access.md` §3.2（54行目）

H6への対応で、親のイベントを常に `getDocFromServer` で取るようになった。この結果、オフラインで起動するとイベントを1件も取得できず、一覧が空になる（「イベントがありません」と出るおそれもある）。SPEC 7.3では、スタッフ画面は通信がなくても開ける必要がある。

**対策**：一覧の表示には、キャッシュも使える `getDoc` を使う。サーバーへの確認（`getDocFromServer`）は、**孤立した `members` を削除するかどうかの判定だけ**に限る。`EventGate` が、保存してある現在のイベントを復元するときに、この一覧に依存していないことも確認する。

### 🟠 新たな指摘（中）

#### N4. 通信が必要な書き込みが、オフラインのときに溜まってしまう
- イベントの作成、参加（`joinEvent`）、招待、レジ締めの保存は、バッチや `set` で書くので、オフラインでも受け付けられて溜まる。その間、画面は完了を待ち続ける。事前にサーバーへの読み取りで通信を確かめるか、タイムアウトを設ける

#### N5. メンバーから外れたときにキャッシュを消すと、他のイベントの未送信まで消える
対象：`design/data-access.md` §8（218行目）

`clearIndexedDbPersistence` は、端末のキャッシュを丸ごと消す。外されたイベントとは別のイベントの未送信の書き込みも消え、画面も突然再読み込みされる。

**対策（決定：未送信がなくなるまで延期）**：`waitForPendingWrites` で、他のイベントの未送信が送られるのを待ってから消す。未送信が残っていれば、消去を次の起動時に持ち越す。

**対策**：「一覧に出さない」のは、**表示用の `getDoc` が `permission-denied` になったときだけ**、と書き分ける。通信エラーとキャッシュからの結果は、「削除はしないが、一覧には出す」。テスト16番も、「`permission-denied` → 出さない」と「オフライン → 出す（削除はしない）」の2つに分ける。

### 🟡 指摘（低）
- **確定が墓標で拒否されたときに、品目が消える**（OC §5.1 91行目、TS §4 の20番）：「やめた注文です」として `pending` を消して `idle` に戻すと、スタッフが「もう一度確定する」を選んで登録しようとしていた品目が失われる。`abandoning` の先行保存により、この経路は通常は起きない（防御のための処理）が、起きたときは、`draft` を残したまま、**新しい `orderId` で確定し直せる**ようにするのが安全
- **`resolvePending` の「同時に1つだけ」の範囲**（OC §5.4）：8秒のタイムアウトは `Promise.race` なので、裏のトランザクションは続く。実行中の判定を「タイムアウトまで」にすると、15秒ごとに、裏のトランザクションが積み重なる（冪等なので、結果は正しい）。「裏のトランザクションが終わるまで、次を始めない」と明記し、その間に手動ボタンを押したときは「確認中です」と返す
- **SPEC 4.3 の「前日以前の注文は変更できない」**：前日の注文がまだ調理中・できあがりのときは、調理画面の通常のカードに「支払い変更」があり、変更できる。「済み（お渡し済み・取り消し）の注文は、当日分のみ」と書くと、実際の動きと一致する
- **イベント一覧・`/join` での接続状態**（DA §3.9 139行目）：「接続状態がオフラインの間は、ボタンを無効にする」とあるが、接続状態の判定は、Shellの購読（イベントを選んでいる間だけ）に依存する。イベント一覧や `/join` では、`navigator.onLine` だけで判定することを明記する（`assertOnline` があるので、実害はない）
- **テストの不足**：メンバーから外れたときの、24時間後の確認（DA §8）と、`resolvePending` が同時に1つだけ動くこと（OC §5.4）が、テストにない。前者は時刻を偽る単体テスト、後者は `confirmReducer` か結合テストに加える
