## 情報

### D1 ℹ️ 450件のバッチ削除と、ルールの評価の上限

**場所**：`src/lib/data/eventDelete.ts`（`DELETE_BATCH = 450`）、`firestore.rules`（`isOwner(eventId) && isDeleting(eventId)`）

**確認したこと**：削除のルールは、文書ごとに、イベント文書の `get()` を呼ぶ（`isOwner`・`isDeleting`）。本番の Firestore には、1回の書き込み（バッチ）で評価できる `get()`・`exists()` の回数の上限がある。同じ文書の呼び出しは、まとめて数えられるはずだが、Emulator の結果（3,000件が6.4秒）では、本番で通るかは分からない。通らないと、450件のバッチが、すべて拒否される。

**対応**：devの確認で、**450件を超える注文**（たとえば600件）があるイベントを作り、削除を通す。件数が少ないと、バッチが1つしか動かず、確かめたことにならない。上限に当たるなら、`DELETE_BATCH` を下げる。

### D2 ℹ️ イベント本体が消えてから、自分の `members` が消えるまで

**場所**：`src/lib/data/eventDelete.ts`（`tick('event')` 以降）、`src/state/eventDelete.ts`、`src/staff/App.tsx`

**確認したこと**：`deleteDoc(eventRef)` の直後、`members/{uid}` を消す前に、アプリのイベントの購読が「イベントが無い」を受け取る。このとき、画面が「見つかりません」のような表示に切り替わると、`DeleteStatus` が見えなくなる。この間に、自分の `members` の削除だけが失敗（時間切れ）した場合、画面に「削除を再開」が出ない。設計書は、この場合を「`watchMyEvents` が、サーバーでイベントが無いことを確認し、削除する」としている。コードの上では、この経路を確かめていない。

**対応**：devで、イベントの削除の最後（「仕上げています」）の直後の画面が、一覧へ自然に戻ることを見る。機内モードを使う確認は、手順5の直後だけ狙うのは難しいので、必須ではない。

### D3 ℹ️ イベント名の一致の判定

**場所**：`src/staff/event/DeleteEventPanel.tsx`（`name.trim() !== event.name`）

**確認したこと**：入力側だけ `trim()` している。イベント名の保存時に前後の空白が落ちていれば問題ない。落ちていない経路（古いデータ、貼り付け）があると、見た目が同じ名前を入力しても、「イベント名が違います」になる。イベント作成時に名前を整えているなら、対応は要らない。

## 確認して問題なかった点

- **`purge` の終了**：読むのは `DELETE_BATCH + 1` 件で、除外する文書（自分の `members`）が混ざっても、450件を消せる。対象が0件になれば返る
- **再開**：毎回 `getDocsFromServer` で読み直すので、途中で止まっても、残りだけを消す。バッチの時間切れで、書き込みがキューに残っても、再実行の削除は、冪等
- **権限**：`ownerUid` が自分でなければ `permission`。イベント文書が無い場合（手順5〜6の間で止まった）は、自分の `members` だけを消す
- **空の確認**：配下の5つ、`invites`、`members`（自分だけ）を見て、残っていれば最大3回やり直す。終わらなければ `conflict`
- **削除中の書き込み**：先に `deleting = true` にし、他のメンバーと招待を消すので、削除中に新しい書き込みを許さない
- **保留中の操作**：`startEventDelete` が、先に `flushAllHolds()` を呼ぶので、消える注文へ、あとから書かない（#51 との整合）
- **オフライン**：最初にイベント文書をサーバーから読む。届かなければ `offline` で、何も始めない。ボタンも、オフラインでは押せない
- **ルール**：`voids` の `list` は、メンバーだけに許す。中身は作成者と時刻だけで、個人情報は無い。ルールのテストがある
- **#52 のトークン名の修正**：`--color-text` → `--color-ink`。PR本文に書かれていて、変更も1行
