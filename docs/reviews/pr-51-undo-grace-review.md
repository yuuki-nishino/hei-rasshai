## 指摘

### H1 🟡 残り時間の帯が、続けての操作で最初からやり直しにならない

**場所**：`src/staff/kitchen/UndoBar.tsx:237`（`key={h.orderId}`）、`src/state/holdStore.ts`（`start`）

**問題**：`start()` は、同じ注文の前の保留を先に書き（`written: true`）、取り除いてから、新しい保留を足す。新しい保留の `orderId` は前と同じなので、`UndoBar` の `key` が変わらず、同じ要素が使い回される。CSSアニメーション（`drain`）は、要素が作り直されないと、最初からやり直しにならない。

**起こりうること**：同じ注文に「完成」→（5秒以内に）「渡した」と押すと、2回目の帯は、途中まで縮んだ状態から始まる。実際の猶予は5秒なのに、帯はそれより短く見える。動作（5秒後に書く・「元に戻す」で何も書かない）には影響しない。見た目だけの食い違い。

**直し方の案**：`Hold` に、連番か開始時刻（`startedAt`）を持たせ、`key` をそれにする。`holdStore.test.ts` の「同じ注文に続けて操作」のテストに、連番（開始時刻）が変わることの確認を足す。

### H2 ℹ️ 画面の消灯・切り替えで、猶予が打ち切られる

**場所**：`src/state/hold.ts`（`visibilitychange`・`pagehide`）

**確認したこと**：画面が見えなくなると、保留中の操作をすぐ書く。5秒以内に端末が自動で消灯したり、別のアプリへ切り替えたりすると、「元に戻す」が使えないまま書かれる。操作が失われないための設計で、意図どおり。

**対応**：PR本文の実機確認に、「押した直後の消灯・切り替え」も加えると確かめやすい。

### H3 ℹ️ 複数のバーが重なる

**場所**：`src/staff/App.tsx`（`ToastRegion` の中の `UndoBar`）、`UndoBar.tsx`

**確認したこと**：保留中の注文ごとに、バーが1つずつ出る。忙しいときに続けて押すと、最大で5秒ぶんのバーが重なり、画面の下を覆う。上限や並び順（新しいものを先頭に、など）は、実機で見て決めれば足りる。

### H4 ℹ️ `UndoBar` 自体のテストは無い

**確認したこと**：`holdStore`（保留・元に戻す・すぐ書く）は、偽のタイマーで十分に押さえてある。結合テストも、お客様の購読に何も届かないことを、本物のルールの下で確かめている。`UndoBar` は表示だけの薄いコンポーネントなので、必須ではない。

## 確認して問題なかった点

- **書き込みの順序**：保留しない操作（「調理中に戻す」など）の前、取り消しの確認後、同じ注文への次の保留の前、ログアウト、イベントを離れるときのどれも、先に `flush` する。保留を反映した状態を元に遷移を判断するので、遷移がずれない
- **取り消し**：`flushHold` の後に `holds.peek()` を反映して判断するので、保留が見えるままで判断できる
- **ログアウト**：`transitionOrder` の `updateDoc` は同期的にキューに入る。`flushAllHolds()` の直後の `hasPendingWrites()` が、書いた分を未送信として数える
- **タイマーの競合**：「書き込み済みの印を消す」タイマーが、新しい保留を消すことはない（`start` が古いタイマーを `clearTimeout` する）。テストにもある
- **お客様の画面**：猶予の間は、サーバーに何も書かないので、お客様に間違った状況が届かない。`customer.html` には触れていない
- **ルール・個人情報**：`firestore.rules` は変更なし。個人のメールアドレスなども増えていない
