# PR #48 レビューへの対応

対象：[pr-48-connection-status-review.md](./pr-48-connection-status-review.md)。あわせて、devの実機の確認（2026-10-08）で出た点も、ここに記録する。

## devの実機の確認で出た点

| 内容 | 対応 | 反映先 |
|---|---|---|
| オフラインからオンラインへの戻りが遅い（オフラインになるのは早い） | **採用**。SDK は、通信が戻っても、間隔を空けて再接続を待つ。ブラウザの `online` イベントで、`fromCache` の数え直しを始め、`reconnectNow()`（ネットワークを一度止めて入れ直す。未送信は残る）で、すぐ再接続させる | DA §6.1、`state/connection.ts`、`lib/data/online.ts` |
| 「未送信◯件」「未送信あり」が出なかった | 再読み込み後の「未送信あり」は、C2（オフライン中は不明の印を無視）が原因。「未送信◯件」は、**数える対象が調理画面の操作（状態・支払い・メモ）だけ**で、メニューの編集などは数えない。手順の注意として記録する（下記） | DA §6.2 |
| ふだんからオンライン・オフラインが出るのは邪魔。通信が不安定なときだけ出してほしい（オンライン前提のアプリのため） | **採用**。オンラインで未送信も無いときは、何も出さない。オフラインは「通信状態が不安定です」（未送信があれば添える） | SPEC §、DESIGN §、SC §2、VS、DA §6.2 |

## レビューの指摘

| # | 判断 | 内容 |
|---|---|---|
| C1 | **採用** | 購読のエラーでも `resetConnection()` を呼ぶ |
| C2 | **採用** | `statusBarView` が、オフラインでも件数・不明を渡す。表示は「通信状態が不安定です（未送信あり）」。単体テストを足した |
| C3 | **一部採用** | 注文の確定はオンライン必須（書き込みを溜めない）、メニューは数えない、という設計のままにする。「不明」が、新しい分も待って残ることは、設計書に書いた（DA §6.2）。入口の一本化は、見送り |
| C4 | **採用** | `onRejected` を `try/catch` で囲む。結合テストを足した |

## 確認の注意（テストの仕方）
- 「未送信◯件」は、**調理画面**で、状態の変更・支払いの変更・メモの変更をしたときに出る（オフラインのまま）。メニューの編集・注文の確定では出ない
