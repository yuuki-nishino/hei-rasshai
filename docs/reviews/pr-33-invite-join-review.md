## 指摘

### J1 🟠 参加の書き込みに時間切れが無く、通信が切れると止まったままになる

**場所**：`src/lib/data/events.ts:109`（`joinEvent`）

**問題**：
- 接続の確認は、最初にメンバーの文書を読むとき（`getDocFromServer`）の1回だけ。そのあとの `await batch.commit()` には、時間切れ（タイムアウト）が無い
- スタッフ用の `db` は、オフライン用の保存領域（`persistentLocalCache`）を使う。この設定では、`commit()` は、サーバーが書き込みを受け取ったと確認できるまで、待ち続ける
- そのため、確認のあとで通信が切れると、いつまでも終わらない

**起こりうること**：電波の弱い会場で、招待リンクを開く。最初の確認は通り、その直後に電波が切れる。

**結果**：
- `JoinPage` が「招待を確認しています…」のまま止まる。エラーも「もう一度」ボタンも出ない
- 参加の書き込み（メンバーの作成と招待の削除）は、端末の中で送信待ちのまま残る。つながり直したときに送られ、通ることもある。その時点で招待の期限（1日）が切れていれば、はじかれる
- 「オフラインで失敗したら、送信待ちの書き込みを残さない」という決まり（[testing.md](../design/testing.md) #23）に反する。新しいテストは、最初からオフラインの場合だけを試しているため、この場合を見つけられない

**直し方の案**：
- `batch.commit()` を `withTimeout(...)` で包み、時間切れになったら `offline` として扱う
- それでも、送信待ちの書き込みは残り、あとで通ることがある。これは避けられないため、そうなるものとして扱う（画面の文言や、設計書への注記）

**参考**：同じ形の問題が、`createEvent`（`src/lib/data/events.ts:133`）にもある。こちらは、この PR より前からあるコード。

### J1 の確認

- `withTimeout` は、時間切れで `AppError('timeout')` を投げ、`finally` でタイマーを止める。元の書き込みは止めない（送信待ちが残るという設計書の説明と一致）
- 画面ごとの案内が、二重になるかどうかに合っている（参加：`already` で止まる／作成：二重になり得るので「一覧で確かめて」／招待：同じ文書の上書き）
- テスト：`getDocFromServer` の後に `disableNetwork` を差し込む方法は、レビューで指摘した場合（確認の直後に切れる）をそのまま再現している。データのテストの時間切れは30秒（`vite.config.ts:53`）なので、8秒＋8秒の待ちでも収まる。後片付けは `closeUsers`（`terminate`）と `clearFirestore` で、送信待ちがほかのテストに漏れない
- 設計書（data-access.md §3.9、testing.md §4）も、同じ PR で直している

### J2 🟡 送信待ちが流れている途中の「もう一度」で、「参加できません」と出ることがある

**場所**：`src/lib/data/events.ts:97`（`joinEvent`）、`src/staff/join/JoinPage.tsx:35`

**問題**：「もう一度」は、まず `getDocFromServer` でメンバーかを確かめる。ところが、通信が戻った直後で、前回の送信待ちがまだサーバーに届いていないと、「メンバーではない」と判断して、もう一度バッチを書く。書き込みは順に送られるため、先に前回のバッチが通り、今回のバッチは「既存のメンバー文書の上書き」になる。ルールは `update: if false`（`firestore.rules:103`）なので拒否され、`permission` になる。

**結果**：実際には参加できているのに、「このアカウントでは、参加できません」の画面になる。イベント一覧へ戻れば、そのイベントは見えるため、害は小さい。ただ、案内としては誤り。

**起こる条件**：時間切れ → 電波が戻る → 送信待ちが流れ切る前（ふつうは1秒未満）に「もう一度」を押す。まれ。

**直し方の案**：バッチが `permission` で失敗したとき、`getDocFromServer(memberRef)` で1回だけ確かめ直し、メンバー文書があれば `'already'` を返す。
