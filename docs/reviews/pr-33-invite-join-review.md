## 指摘

### J1 🟠 参加の書き込みに時間切れが無く、通信が切れると止まったままになる

**場所**：`src/lib/data/events.ts:109`（`joinEvent`）

**問題**：
- 接続の確認は、最初にメンバーの文書を読むとき（`getDocFromServer`）の1回だけ。そのあとの `await batch.commit()` には、時間切れ（タイムアウト）が無い
- スタッフ用の `db` は、オフライン用の保存領域（`persistentLocalCache`）を使う。この設定では、`commit()` は、サーバーが書き込みを受け取ったと確認できるまで、待ち続ける
- そのため、確認のあとで通信が切れると、いつまでも終わらない

**起こりうること**：電波の弱い会場で、招待リンクを開く。最初の確認は通り、その直後に電波が切れる。

**結果**：
- `JoinPage` が「招待を確認しています…」のまま止まる。エラーも「もう一度」ボタンも出ない
- 参加の書き込み（メンバーの作成と招待の削除）は、端末の中で送信待ちのまま残る。つながり直したときに送られ、通ることもある。その時点で招待の期限（1日）が切れていれば、はじかれる
- 「オフラインで失敗したら、送信待ちの書き込みを残さない」という決まり（[testing.md](../design/testing.md) #23）に反する。新しいテストは、最初からオフラインの場合だけを試しているため、この場合を見つけられない

**直し方の案**：
- `batch.commit()` を `withTimeout(...)` で包み、時間切れになったら `offline` として扱う
- それでも、送信待ちの書き込みは残り、あとで通ることがある。これは避けられないため、そうなるものとして扱う（画面の文言や、設計書への注記）

**参考**：同じ形の問題が、`createEvent`（`src/lib/data/events.ts:133`）にもある。こちらは、この PR より前からあるコード。

## 問題なしと確認した点

- ルールが、まとめて行う書き込み（メンバーの作成と招待の削除）と一致している
- メールアドレスを小文字にそろえる処理が、画面側とルールで同じ
- `/join` の画面が、Hosting の `**` の転送設定で正しく開く
- 「このアカウントでは、参加できません」の画面から入り直すと、招待をもう一度確認する
- 招待の作成・出し直し・取り消しは、どれも先に接続を確認している
