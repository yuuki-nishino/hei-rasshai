## 指摘

### P1 🟠 削除中・削除後のイベントにも、参加できる

**場所**：`firestore.rules` の `match /members/{uid}` の `allow create`（role = member の分岐）

**問題**：参加のルールは、招待の有無と期限を確かめる。しかし、**イベントがあるか、`deleting` 中か**は、確かめていない。

**起こりうること**：
1. オーナーが、イベントの削除を始める（[data-access.md](../design/data-access.md) §7）。手順 2 で、他のメンバーと招待の一覧を取る
2. オーナーが一覧を消し終わる前に、招待された人が参加する（`members` を作り、招待を削除する）
3. 結果：
   - 削除中のイベントに、新しいメンバーが増える
   - そのメンバーは、メニューなどに書き込める。手順 5 の「空の確認」でやり直しにはなる
   - イベントが消えた後に、`members` が残る
   - 招待が消し残された場合は、**存在しないイベントにも参加できる**

**今の手当て**：残った `members` は、`watchMyEvents` の孤立の掃除で、後から消える。そのため、致命的ではない。

**直し方**：参加の分岐に、次を足す。

```
&& exists(eventPath(eventId)) && get(eventPath(eventId)).data.deleting == false
```

- 同じ文書の `get` は、1回の評価の中では、まとめて1回の読み取りとして数えられるはず。そのため、追加の読み取りは少ない
- 招待の作成・更新（`invites` の `allow create, update`）にも、`deleting == false` を足すと、筋が通る

**足すテスト**：
- `deleting = true` のイベントには、有効な招待があっても、参加できない
- 存在しないイベントには、招待が残っていても、参加できない
- `deleting = true` のイベントでは、オーナーも招待を作れない

### P2 🟡 オーナーの `members` を作らずに、イベントだけを作れる

**場所**：`firestore.rules` の `match /events/{eventId}` の `allow create`

**問題**：
- ルールが強制しているのは、「`members`（owner）は、イベントがあるときだけ作れる」という方向（`getAfter`）だけ
- 逆の「イベントを作るときは、同じバッチで `members` も作る」は、強制していない
- そのため、[security-rules.md](../design/security-rules.md) §4 の「1バッチ」は、片方の方向からしか守られていない

**起こりうること**：
- `members` の無いイベントは、オーナーにも見えない（`isMember` が通らないため。`watchMyEvents` の一覧にも出ない）
- `deleting` を立てられない（更新に `isMember` が必要）ので、削除もできない

**今の手当て**：オーナーは、owner の `members` を後から作れる（P3）。そのため、元には戻せる。

**直し方**：イベントの作成に、次を足す。

```
&& existsAfter(subPath(eventId, 'members', request.auth.uid))
```

**テストの名前**：`events.test.ts` の「イベントだけでなく、オーナーの members も、イベントと同じバッチでないと作れない（R2）」は、名前と中身がずれている。今試しているのは、「イベントが無いと、`members` を作れない」という方向。直すときは、次の2つに分ける。
- イベントが無いと、owner の `members` を作れない（今のテスト）
- owner の `members` を作らないと、イベントを作れない（P2 の修正のテスト）

### P3 ℹ️ owner の `members` の作成が、「イベントと同じバッチ」に限られていない

**場所**：`firestore.rules` の `members` の `allow create`（role = owner の分岐）

**問題**：
- コメントは「オーナー：イベントと同じバッチで作る」となっている
- しかし、ルールは `getAfter(eventPath(eventId)).data.ownerUid == uid` を見ているだけ。そのため、オーナーは、いつでも自分の `members` を作り直せる

**影響**：オーナーは、イベントがある間は抜けられない。そのため、害はない（P2 の復旧手段にもなる）。

**直し方**：コメントを、実態に合わせる。例：「オーナー：イベントの `ownerUid` が自分なら作れる（作成は、イベントと同じバッチで行う）」。

### P4 🟡 `fieldOverrides` で、コレクション単位の自動の索引が無効になる

**場所**：`firestore.indexes.json`

**問題**：
- `fieldOverrides` は、その項目の自動の索引を**置き換える**
- この PR は、`members.uid` をコレクショングループ単位の昇順だけにしている
- そのため、コレクション単位の自動の索引（昇順・降順・`array-contains`）は無効になる

**影響**：
- 今は、1つのイベントの `members` を `uid` で絞る検索は予定されていない。そのため、実害はない
- Emulator は索引を検査しない。そのため、ルールのテスト（R3 の、個別のイベントの `members` の検索）では、気づけない

**直し方**：次のどちらか。
- コレクション単位の3つも並べて、自動の索引を残す
- 無効にすることを、[data-model.md](../design/data-model.md) §4 に書いておく

devで `npx firebase firestore:indexes -P dev` の出力を見れば、実際の状態を確かめられる。

### P5 ℹ️ `creators` の文書IDは、小文字が前提

**問題**：ルールは、`myEmail()`（トークンのメールを小文字にしたもの）で、`creators/{email}` を照合する。そのため、Firebaseコンソールで、`creators` に大文字を含むIDを登録すると、そのアカウントは、イベントを作れなくなる。

**直し方**：`creators` の登録手順（運用の文書）に、「メールアドレスは、小文字で登録する」と書く。

## 良い点

- **R3 の分析**：ルールが「フィルターではない」ことを踏まえて、攻撃する側の目線で、抜け道を試している（`in`・`!=`・範囲・他の項目）。さらに、「結果が空」「イベントの有無が分からない」まで、テストで確かめている
- **テストの強さの確認**：ルールの要の行を1行ずつ壊して、テストが失敗することを確かめている（ミューテーションテスト）
- **境界のテスト**：招待の期限（23時間／25時間）、メールの大文字、`email_verified = false`、ID に使える記号まで、押さえている
- **型の分離**：`tsconfig.test.json` を分けたことで、アプリ側の型に `node` が混ざらなくなった
- **テストの分割**：Vitest の `unit`・`rules` の2つに分けている
- **CI**：Java 21 と Emulator のキャッシュを入れて、ルールのテストを CI で実行するようにした

## その他（対応は任意）

- **期限のテストの時計**：境界のテスト（23時間／25時間）は、手元の時計の `Date.now()` と、Emulator の `request.time` の差に頼っている。ただし、1時間の余裕があるので、問題ない
- **`npm test` に Java が必要になった**：手元で単体テストだけを回したい人は `npm run test:unit` を使う、という点は、CLAUDE.md に書かれていて十分
- **`displayName` の最小の長さ**：`displayName` は、空文字でも通る。[data-access.md](../design/data-access.md) §3.9 の規則で、クライアントが必ず値を入れるなら、そのままでよい
