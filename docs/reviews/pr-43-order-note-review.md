## 指摘

### N1 🟡 テスト名と中身が合っていない

**場所**：`test/data/orders.test.ts`（`changeNote：お渡し済み・取り消しの注文のメモも変えられる`）

**問題**：
- 手順は、調理中の注文のメモを変え、取り消してから、もう一度変える、というもの。「お渡し済み」（`done`）の状態には、一度もしていない
- 「お渡し済み」のメモが変えられることは、ルールのテスト（`status: 'done'` のシード）が確かめている。ただ、このテストだけを読むと、確かめたように見える

**直し方の案**：`done` にしてからメモを変える手順を足す。または、テスト名を「取り消しの注文」に絞る。

### N2 🟡 「確定」の行に、`note` を書くことが書かれていない

**場所**：`docs/design/data-model.md` §3（状態遷移の表の「確定」の行）

**問題**：
- 「確定」の行は、作成時の初期値（`cancelledFrom = null` など）を挙げるが、`note` には触れていない
- コードは、確定のときに `note` を必ず書く（メモなしなら空の文字列）。§2 の「項目が無い・空は、メモなし」と矛盾はしない

**直し方の案**：「確定」の行に、「`note` は、入力したメモ（無ければ空）」と一言足す。

### N3 ℹ️ そのほか

- **表の行の位置**：`security-rules.md` の「R7 の追加（#40）」の行が、R10 と R11 の間にある。R7 の行の直後に置くと探しやすい
- **メモの置き場所**：
  - 注文のデータは、注文IDを知っている人（お客様）が読める。メモも、技術的には読める
  - 設計書は、入力欄の注意書き（個人の名前などを書かない）で運用している。CLAUDE.md の「個人情報を、お客様が読める場所に保存しない」を、注意書きで守る形
  - スタッフ専用の別ドキュメントに置く案もある。ただし、読み込みが増え、無料枠にも影響する。今の判断は、設計書に書かれている。ADR を足すかは、任せる
- **テストの不足**：「クリア・確定の成功で、メモが空になる」（`state/cart.ts`）には、テストが無い。小さな処理なので、必須ではない

## 確かめて、問題が無かったこと

- **ルール**：
  - `validNote` は `d.get('note', '')` を使う。`note` の無い古い注文でも、状態の更新・支払いの変更が通る
  - `note` は、作成時（`hasOnly` と `validNote`）と更新時（`affectedKeys` と `validNote`）の両方で許される
  - 文字数は UTF-16 の単位で、画面側の `normalizeNote` と同じ数え方。画面が受け付けたメモが、ルールに拒否されることはない
- **古い pending**：`confirmOnce` の `ctx.draft.note ?? ''` が、メモの項目が無い記録を扱う。復元の確認は、`orderId` と `draft.items` だけを見るので、古い記録も復元される
- **メモのダイアログ**：開くたびに、現在のメモから入力欄を作る。保存は、開いたときの注文に対して行う。開く・閉じる・Esc も正しく動く
- **文字数の上限**：カートの入力と確定の段階の両方で、`normalizeNote` が上限を守らせる
- **テスト**：ルールのテストは、通る場合（項目なし・空・100文字ちょうど・取り消し済み・状態変更と同時）と、拒否される場合（101文字・絵文字51個・数値・真偽値・`null`・リスト・品目の同時書き換え・不正な `updatedBy` / `updatedAt`・非メンバー）を確かめている。データアクセスのテストは、確定・再確定・古い pending・古い注文・`changeNote`・購読・オフラインを確かめている
- **設計書**：SPEC・data-model・data-access・security-rules・screens・order-confirm・testing の記述は、コードと矛盾しない。お客様画面にメモを出さないことは、3か所で一貫している
