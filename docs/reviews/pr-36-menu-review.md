## 指摘

### M1 🟡 フォーカスして外すだけで、ほかのメンバーの変更を上書きする

**場所**：`src/staff/menu/MenuPage.tsx:173-176`（同期の `useEffect`）、`:178-189`（`commitName`）、`:191-202`（`commitPrice`）

**問題**：
- 編集中の欄（`editing`）には、ほかのメンバーの変更を反映しない（173-176行目。設計どおり）
- 一方、`commitName` は、入力欄の値を、**いまの `item.name`**（＝ほかのメンバーの変更後の値）と比べて、違えば書く（188行目）。価格（201行目）も同じ
- そのため、利用者が値を変えていなくても、フォーカスしている間に、ほかのメンバーが同じ欄を変えると、外したときに、古い値で書き戻す

**起こりうること**：スタッフAが、「焼きそば」の価格の欄をタップする（キーボードが出たまま、別の作業をする）。その間に、スタッフBが、同じ品の価格を 500 → 600 に変える。Aが、何も入力せずに欄の外をタップする。

**結果**：価格が 500 に戻る。AもBも、戻ったことに気づきにくい。注文画面では 500 円で売られる。

**直し方の案**：
- フォーカスしたときの値（`base`）を覚え、確定のときは `base` と比べる。変えていなければ、書かずに、`item` の値へ同期し直す
  ```ts
  const base = useRef({ name: item.name, price: item.price });
  // onFocus で base.current を item の値にする
  // commitName：if (n === base.current.name) { setName(item.name); return; }
  ```
- 利用者が変えていて、かつ `base` と `item` が違う（編集中に、ほかの人も変えた）ときは、後勝ちで書くか、知らせるかを決める（後勝ちで足りると思う）

### M2 🟡 確定の直後に、元の値が一瞬表示される（★要確認）

**場所**：`src/staff/menu/MenuPage.tsx:173-176`、`:178-189`

**問題**：
- `commitName` は、`setEditing(null)` と `setName(n)` を呼んだ後に、書き込む（`onUpdate`）
- `editing` が変わるため、描画の後に、173行目の `useEffect` が動き、`setName(item.name)` で、**まだ書き込み前の値**に戻す
- 書き込みが購読（`watchMenu`）に届くのは、永続キャッシュ（IndexedDB）への書き込みの後。Preact の `useEffect` は、描画の後（次のフレーム）に動く。どちらが先かは、端末の速さによる
- 後者が先なら、「新しい値 → 古い値 → 新しい値」と、ちらつく。価格を「1,000円」と入れたときは、「1000」→ 元の価格 → 「1000」になる

**直し方の案**：
- 同期の `useEffect` の依存から `editing` を外し、`item.name`・`item.price` が変わったときだけ同期する（編集中かは `useRef` で見る）。M1 の `base` と合わせて直すと、まとまる
- 低速の端末（dev の実機）で、ちらつきが見えるかを確かめる（コードを読んだ結果で、実機では確かめていない）

### M3 🟡 編集中にタブを切り替えると、入力が消える端末がありうる（★要確認）

**場所**：`src/staff/menu/MenuPage.tsx:218`・`:229`（`onBlur` でだけ保存）、`src/staff/App.tsx:50`（タブで `MenuPage` を外す）

**問題**：
- インライン編集は、`blur` でだけ保存する
- タブ・「一覧へ」を押すと、`MenuPage` が外れる。フォーカスのある入力欄が、DOM から取り除かれるとき、`blur` が届くかは、ブラウザによって違う（仕様では、取り除くときに `blur` は出ない）
- パソコンのブラウザでは、ボタンを押した時点で入力欄からフォーカスが外れるため、先に `blur` が届く。iOS の Safari は、ボタンを押してもフォーカスを移さないため、入力欄にフォーカスが残ったまま、外れる可能性がある

**起こりうること**：iPhone で、価格を書き換え、キーボードを閉じずに、「注文」タブを押す。

**結果**：変更が、知らせのないまま保存されない（保存されたと思い込む）。

**直し方の案**：
- dev の iPhone で、上の手順で保存されるかを確かめる
- 保存されないなら、行の `useEffect` の後片付け（外れるとき）で、編集中の値を確定する。または、タブの `onSelect` の前に `document.activeElement?.blur()` を呼ぶ

### M6 🟡 タブに、`tabpanel` が無い

**場所**：`src/components/Tabs.tsx:21-37`、`src/staff/App.tsx:48`

**問題**：
- `role="tab"` は、対応する `role="tabpanel"` を `aria-controls` で指すことが前提（WAI-ARIA の Tabs のパターン）
- 今は、`tab` だけがあり、中身（`<main>`）との結び付きが無い。読み上げでは、「タブ、3つのうち2つ目、選択済み」と読まれるが、中身へ移る手がかりが無い

**直し方の案**：
- `<main>` に `role="tabpanel"`・`id`・`aria-labelledby`（選んでいるタブの `id`）を付け、各タブに `aria-controls` を付ける
- 小さい対応で済ませるなら、`role="tablist"`・`role="tab"` をやめ、`aria-current="page"` の付いたボタンの並びにする（URL を持たない画面の切り替えなので、どちらでもよい）

### M7 ℹ️ そのほか（直さなくてよい。記録のため）

- **100件の上限は、端末だけで守る**（`src/lib/data/menu.ts:56`）。2台で同時に追加すると、101件以上になりうる。ルールでは件数を数えられないため、data-model.md §2.5 の「最大100件まで」に、「端末の検査で守る（同時の追加で、わずかに超えることがある）」と書いておくとよい
- **`addMenuItem` は、名前・価格を検査しない**（`src/lib/data/menu.ts:55`。`updateMenuItem` は検査する）。今の呼び出し元は、画面で検査済みなので困らない。オフラインで不正な値を足すと、つながるまで一覧に出てしまうため、後の呼び出し元のために、`updateMenuItem` と同じ検査を入れてもよい
- **`parsePrice` は、カンマの位置を見ない**（`src/lib/domain/menu.ts:24`）。「1,00」は 100 になる。打ち間違いを通すが、実害は小さい
- **▲で先頭に動かすと、ボタンが無効になり、フォーカスが消える**（`MenuPage.tsx` の `.move`）。キーボードで操作する人は、位置を見失う。気になるなら、無効にせず、押しても何もしないようにする
- **行の見た目は、`Card` を使わず、独自に書いている**（`MenuPage.module.css` の `.item`・`.soldOutItem`）。visual.md の `Card`（`muted`：地の色にする）と、役割が重なる
