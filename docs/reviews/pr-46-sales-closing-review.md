## 指摘

### C1 🟠 締める金額が、古い集計から作られる

**場所**：`src/staff/closing/ClosingPage.tsx`（`expected` の算出と `save()`）

**問題**：
- `expected`（あるはずの現金）は、`loaded.summary.cashTotal` から作られる。`loaded` は、画面を開いたとき・日付を変えたとき・「更新」を押したときの取得結果
- `save()` は、取得し直さずに、この `expected` を `saveClosing` に渡す。コードのコメントと設計書（screens.md §3.7）は、「サーバーから取得した、いまの現金売上で締める」という説明だが、実際は、取得した時点のもの

**起こりうること**：
1. スタッフ A が、レジ締めの画面を開く（現金売上 15,000円）
2. 別のスタッフ B が、現金の注文を追加する、取り消す、または支払い方法を変える（現金売上が変わる）
3. A が、画面の数字のまま、実際の現金を入れて「締める」を押す
4. 保存される `expectedCash` と `diff` は、古い売上から計算されたもの
5. 次に開くと、締めたばかりなのに、「締め後に変更あり」が出る

保存される値は、画面に出ていた値とは一致するので、「見たものを保存した」という見方もできる。ただ、レジ締めは金額の記録なので、直すことを勧める。

**直し方の案**：
- `save()` の中で、`fetchOrdersOfDayFromServer` をやり直し、その結果から `expected` を作る
- 画面の数字と変わったときは、書き込まずに、新しい数字を見せて、確かめてから保存する
- 直さない場合は、コメントと screens.md の「いまの現金売上」を、「取得した時点の現金売上」に合わせる

### C2 🟡 準備金の変更で、フォームが一瞬消える

**場所**：`src/staff/closing/ClosingPage.tsx`（取得の副作用。依存は `[eventId, day, reload, online, eventFloat]`）

**問題**：
- `eventFloat`（イベントの準備金）が依存に入っている。他のメンバーが準備金を変えると、副作用が走り直し、状態が「読み込み中」になる
- フォームが消え、サーバーへの読み取りも増える。入力中の値は残るが、フォーカスは失われる
- 準備金は、初期値にしか使っていない

**起こりうること**：まれ（準備金が変わったときだけ）。入力中に、画面が一瞬、読み込み中に戻る。

**直し方の案**：`eventFloat` を依存から外す。または、ref 経由で読む。

### C3 🟡 テストが、同じ入力を繰り返している

**場所**：`test/domain/closing.test.ts`（`既知の制約：…相殺されると、検知できない`）

**問題**：
- 直前の「売上が同じなら、変更なし」と、同じ入力（`cashTotal: 15000`）で、同じ結果を確かめている
- 相殺される変更（現金→PayPay と PayPay→現金が、同額）を作っていないため、名前から受ける印象と、中身が合わない

**直し方の案**：テストを消す。または、名前を「合計が同じなら、区別できない」ことが分かるものにする。

## 確かめて、問題が無かったこと

- **ルール（`validClosing`）**：`saveClosing` が書く値（`diff == actual − expected`、上限、メモ200文字、`closedAt`、`closedBy`）と合っている
- **「締め後に変更あり」**：保存済みの準備金と、保存済みの `expectedCash` で判定する。結合テストが、追加・取り消し・戻し・支払い方法の変更・PayPay の追加・締め直しを、本物のルールの下で確かめている
- **集計**（`summarize`）：取り消しの除外、同じ品目の合算、価格が違えば別の行にすること、名前は最新の注文のもの、並び順を、単体テストが確かめている
- **オフライン**：取得（`getDocFromServer`・`getDocsFromServer`）も保存も、サーバーを使う。書き込みが溜まらないことを、結合テストが確かめている
- **日付**：`addDays` は暦の計算で、月・年・うるう日をまたいで、単体テストが確かめている
- **設計書**：SPEC §6.4、data-access.md §3.7、screens.md §3.7、testing.md は、コードと矛盾しない（C1 の「いまの現金売上」の言い回しを除く）

### 確かめて、問題が無かったこと

- **C1**：`save()` が、書く前に `fetchOrdersOfDayFromServer` で取り直す。現金売上が画面と違えば、書かずに、新しい集計を画面に出し、「旧 → 新」を知らせる。あるはずの現金は、準備金と現金売上だけで決まるので、比べるのが `cashTotal` だけで足りる。取り直しの失敗は、既存の `catch` が表示する。screens.md §3.7 の言い回しも、コードに合った。自動テストは無い（画面のテストの仕組みが無いため）ので、対応記録のとおり、Emulator と dev での確認が要る
- **C2**：`eventFloat` を ref 経由で読み、依存から外した。ref を更新する副作用は、取得の副作用より前に宣言されているので、初期値には、最新の準備金が入る。表示用の `closingView(…, eventFloat)` は、そのまま props を使うので、変更は即座に反映される
- **C3**：名前と中身が、「合計だけで判定する」に合った。入力は、保存済みの値から作られ、意図が分かる
- **タブの幅**：最小幅をなくし、文字を `clamp` で縮めて、`nowrap` にした。CSS の見た目は、読んだだけで、画面では見ていない

### ℹ️ 取り直しの間に日付を変えたとき

`save()` の取り直しは、呼んだときの `day` で行う。待っている間に日付を変えると、古い日の集計が、`setLoad` で画面に入る可能性がある（金額が違うときだけ。直後に、日付の変更による取得が上書きするが、順序は保証されない）。ボタンは、保存中は押せないが、日付の選択は、保存中も押せるように見える。まれで、書き込みはされない。直すなら、保存中は `DaySelector` を無効にする。
