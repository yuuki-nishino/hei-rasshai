- 日付：2026-10-05
- 判断：**採用**＝指摘どおり反映／**修正して採用**＝方針は採用し、やり方を変えた／**対応不要**＝すでに満たしている／**見送り**＝反映しない
- 反映先の略称：RU＝`firestore.rules`、IX＝`firestore.indexes.json`、SR＝`design/security-rules.md`、DM＝`design/data-model.md`、DS＝`DESIGN.md`、T＝`test/rules/`
- すべて、PR #26 の中で反映した

| # | 判断 | 内容と理由 | 反映先 |
|---|---|---|---|
| P1 | **採用** | 参加（`members` の作成、role = member）に、`isActiveEvent`（イベントがあり、`deleting == false`）を足した。削除の途中で、メンバーが増えたり、消し残した招待で、存在しないイベントに参加できたりしないようにする。招待の作成・再発行にも、同じ条件を足した。**招待の削除は、削除中でも許可したまま**にする（イベントの削除の手順 2 で、オーナーが招待を消すため）。`isOwner` と同じイベントの文書を読むため、ルールの読み取りは、ほぼ増えない | RU、SR §3・§4、T（members・invites） |
| P2 | **修正して採用** | イベントの作成に、`getAfter(members/{自分}).data.role == 'owner'` を足した。レビューの案（`existsAfter`）より一歩強く、**同じバッチの `members` が owner であること**まで求める。ただし、role = member の `members` は、招待が要るため、イベントと同じバッチでは、もともと作れない（招待の作成は `get` で、作成前のイベントを読むため拒否される）。読み取りの回数は、`existsAfter` と同じ | RU、SR §3・§4、T（events） |
| P2（テスト名） | **採用** | 名前と中身がずれていたテストを、「イベントが無いと、owner の `members` を作れない」と「owner の `members` を同じバッチで作らないと、イベントを作れない」の2つに分けた | T（events） |
| P3 | **採用** | コメントを実態に合わせた。「`ownerUid` が自分なら作れる（作成は、イベントと同じバッチで行う。バッチの外でも作れるが、オーナーはイベントがある間は抜けられないため、害はない）」。ルールは変えない（P2 で、`members` の無いイベントは作れなくなったが、手での操作などで生じたときの復旧手段として、残す） | RU、SR §3 |
| P4 | **採用** | `fieldOverrides` に、コレクション単位の自動の索引（昇順・降順・`array-contains`）も並べ、無効にならないようにした。置き換えになる理由を、DM §4 に書いた。dev にデプロイし、`firebase firestore:indexes -P dev` で確かめる | IX、DM §4 |
