# ADR-0004: 注文確定の「やめる」は、墓標（voids）で排他する

- 状態: 採用（Accepted）
- 日付: 2026-10-03

## 背景

- SPEC 5：「やめる」を選んだ後に、遅れて注文が登録されてはいけない（見えない注文ができてはいけない）
- 注文の確定は、`runTransaction` で行う。8秒でタイムアウトとして画面にはエラーを出すが、トランザクション自体は、キャンセルできず、裏で続く。すでに送信したコミットが、弱い電波で、遅れてサーバーに届くこともある
- 当初の案は、「やめる」の前に16秒待ってから、`getDocFromServer` で存在を確認する、というものだった。前提は、「SDKのトランザクションは、15秒を超えて再試行しない」。しかし、SDKは、時間ではなく試行回数（既定5回）とバックオフで制限し、`unavailable` も再試行の対象になる。**この前提は、保証できない**。また、送信済みのコミットが、16秒より後に届く可能性も、排除できない

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A | 「やめる」の前に、一定時間待ってから、存在を確認する | SDKの内部の挙動と、電波の状況に依存する。Emulatorでは再現しにくく、検証で安全を示せない |
| **B** | **墓標（`voids/{orderId}`）を作ることで、その注文IDの登録を拒否する** | 時間に頼らない。Firestoreのトランザクションとセキュリティルールの原子性で、片方だけが成功する |
| C | 「やめる」を無くし、常に再試行する | SPECの「やめる」を満たせない。オフラインが続くと、スタッフが身動きできない |

## 決定

B案（墓標）を採用する。

- 「やめる」は、トランザクションで、`orders/{orderId}` が**存在しない**ことを確かめてから、`voids/{orderId}` を作る。存在すれば、成功扱い（番号とQRを出す）
- ルール：
  - 注文の作成は、`!exists(voids/{orderId})` のときだけ許可
  - 墓標の作成は、`!exists(orders/{orderId})` のときだけ許可
- どちらが先にコミットしても、後の書き込みは、ルールで拒否される。したがって、「やめる」の後に、遅れて注文が登録されることはない
- 再試行は、同じ `orderId` で、**待たずに**行ってよい。確定のトランザクションは、注文が既にあれば、それを返す（冪等）。これが「再試行前の確認」を兼ねる
- 墓標は、イベントの削除まで残す
- 「やめる」の開始前に、`pending.abandoning = true` を保存する。復元時の確認では、注文と一緒に墓標も確認する（墓標があれば「やめた」と扱う）
- 「確認できない」（`unverifiable`）からは、接続状態の回復・15秒ごとの自動再試行・手動ボタンで抜ける。電波が弱いだけのときは、`online` イベントが発火しないため、起動と `online` だけをきっかけにしない（[order-confirm.md](../design/order-confirm.md) §5.4）

## 結果

- 良い点: 時間への依存がなくなる。「やめる」と遅れたコミットの競合を、Emulatorで、決まった結果として自動テストできる。再試行の待ち時間が不要になる
- 悪い点・リスク: コレクションとルールが1つ増える。「やめる」の書き込みが、オンラインでしかできない（オフラインのときは、`pending` に残し、復帰後に実行する）。ルール内の `exists()` が、トランザクションの競合の下でも、一貫した結果を返すことに依存する（★R8：Emulatorで、順序と競合の両方を検証する）
- Emulatorは、本番と同じ並行性を再現するとは限らない。競合のテストは補助とし、安全性は、順序の2ケースのテストと、「コミット時にルールが評価されること」に置く
- 見直す条件: ★R8で、競合時に両方が成功するケースが見つかった場合
