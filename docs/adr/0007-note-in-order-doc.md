# ADR-0007: 注文のメモは、注文の文書に置く（スタッフ専用の別の文書にしない）

- 状態: 採用（Accepted）
- 日付: 2026-10-06

## 背景

- 注文時に「辛さ抜き」などのメモを残し、調理画面で目立たせる。確定後も修正できる（Issue #40）
- お客様は、注文IDを知っている注文1件を、**文書まるごと**読める（`orders/{orderId}` の `get: if true`。お客様画面のため）。Firestore は、項目ごとに読み取りを制限できない
- そのため、注文の文書に置いた項目は、お客様画面に出さなくても、**技術的には**、注文のQRの持ち主（お客様）や、そのURLを知る人が、読める（ブラウザの開発者ツールなどで）。注文ID・イベントIDは、推測できない20文字の自動ID
- 支払い方法・メモなどが該当する。CLAUDE.md には「個人のメールアドレスなどを、お客様が読める場所に保存しない」とある

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | **注文の文書に `note` として置く。個人情報を書かないよう、入力欄で注意する** | 追加の読み取りが要らない（調理画面は、注文の購読で、メモも一緒に届く）。実装が単純。メモの書き込みも、1文書で済む。お客様に読まれうるのは、「辛さ抜き」程度の内容に限られる（個人情報を書かない運用） |
| B | スタッフ専用の別の文書（例：`orderNotes/{orderId}`）に置く | お客様は、技術的にも読めない。ただし、調理画面が、注文ごとにメモを読む（または、メモのコレクションを購読する）ため、**読み取りが増え**、無料枠に影響する。確定とメモの書き込みを、同じバッチにする必要がある。ルールと設計が増える |
| C | 公開用とスタッフ用に、注文の文書を分ける（SPEC の将来の拡張） | お客様に見せたくない項目（支払い方法・メモ）を、まとめて隠せる。ただし、注文の作成・更新が2文書になり、番号・墓標・遷移のルールが大きく変わる |

## 決定

A を採用する。

- メモは、注文の文書の `note`（任意・100文字まで）。入力欄に、「調理画面に出ます（お客様の画面には出ません）。個人の名前など、個人情報は書かないでください」と添える
- お客様画面は、メモを**表示しない**。取得する項目を、選ぶこともできないため、データとしては届くが、画面には出さない
- 支払い方法も、同じ性質（お客様画面に出さないが、データには含まれる）

## 結果

- 良い点：読み取り・書き込みの回数が増えない（無料枠に影響しない）。調理画面に、メモが、注文と一緒に届く
- 悪い点・リスク：注文のQRを持つお客様は、技術的には、メモを読める。個人情報を書かない運用に頼る
- 見直す条件：メモに、お客様に見せたくない内容を書きたい要望が出た場合。または、支払い方法も含めて、公開用とスタッフ用に文書を分けたくなった場合は、C 案を検討する（SPEC §9 の将来の拡張）
