# ADR-0001: UIライブラリに Preact を採用する

- 状態: 採用（Accepted）
- 日付: 2026-10-03

## 背景

- スタッフ画面は、カート、調理ボード、売上、メニュー編集など、状態が多く、Firestoreのリアルタイム購読で頻繁に再描画される。
- お客様画面は、会場の弱い電波で、初回の読み込みが軽いことが最優先。
- 無料運用・個人開発で、保守できる量に収めたい。

## 検討した選択肢

| 案 | 長所 | 短所 |
|---|---|---|
| 素のDOM + TypeScript | 依存ゼロ。最小サイズ | 購読で更新される一覧・カート・モーダルの再描画を自前で管理する必要があり、状態の不整合が起きやすい。コード量が増える |
| **Preact（+ hooks / signals）** | 約4KB。React互換のAPIで、情報とライブラリが豊富。宣言的に書け、状態管理が楽。Viteの公式プリセットがある | 依存が1つ増える。ごく一部、Reactとの差異がある |
| React | エコシステムが最大 | 約40KB以上。この規模では過剰で、お客様画面の初回読み込みに不利 |
| Svelte / Solid | 小さく速い | 採用実績・情報量・自分の習熟でPreactに劣る。コンパイラ依存が増える |

## 決定

Preact を採用する。

- お客様画面（`/s`）は、別エントリにして、スタッフ側のコードを読み込まない（Preact本体のみ）。
- 状態管理は、まず hooks で書き、共有が必要になった箇所だけ `@preact/signals` を使う。
- React用ライブラリが必要になった場合は `preact/compat` で対応する。ただし、極力使わない。

## 結果

- 良い点: 状態管理が楽。サイズが小さい。後からReactへ移行しやすい。
- 悪い点・リスク: 依存が1つ増える。`preact/compat` で動かないライブラリがあり得る。
- 見直す条件: お客様画面の初回読み込みが目標を超えた、または、互換性の問題が頻発した場合。
