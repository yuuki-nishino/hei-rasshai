# ADR-0005: スタッフ用とお客様用を、別々にビルドする

- 状態: 採用（Accepted）
- 日付: 2026-10-04

## 背景

- お客様画面は、会場の弱い電波で開くため、初回の読み込みを軽く保つ（ADR-0001、DESIGN.md §4・F1：JavaScriptがgzip後200KB以下）
- スタッフ用は、Firestoreの永続キャッシュ（IndexedDB）と Auth を使う。お客様用は、Firestore（メモリキャッシュ）だけを使う（data-access.md §1）
- 当初は、Viteのマルチページ構成（1回のビルドで、`index.html` と `customer.html` を出力）としていた
- #2 で、両方の初期化と `getDoc` 1回の、検証用のコードを入れてビルドしたところ、次のことが分かった
  - Firestore SDK（`@firebase/firestore`）は、両方のエントリから使われるため、**1つの共有チャンク**になった（gzip後 162KB）。Auth は、スタッフ用のチャンクに分かれ、お客様用には入らなかった
  - 共有チャンクには、**スタッフ用の永続キャッシュのコード**（IndexedDBのオブジェクトストア `remoteDocuments` など）が含まれ、お客様用のページも、これを読み込んでいた
  - 原因：バンドラーは、1つのモジュールを、1つのチャンクにしか置かない。不要なコードの削除（tree-shaking）は、両方のエントリで使う部分の和で行われる

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A | マルチページのまま（現状） | お客様用が、使わない永続キャッシュのコードを読み込む（約26KB、gzip後）。スタッフ用の機能が増えるほど、お客様用も重くなる |
| B | `manualChunks` などで、チャンクの分け方を調整する | 同じモジュールを、2つのチャンクに分けて置くことはできない。Firestore SDKの中身を、エントリごとに削ることはできない |
| C | お客様用の Firestore を、REST API（`fetch`）で読む | SDKが要らず、最も軽い。ただし、リアルタイム購読（`onSnapshot`）の代わりに、ポーリングが必要で、読み取りの無料枠を消費する（DESIGN.md §7 の方針に反する） |
| **D** | **スタッフ用とお客様用を、別々のビルドにする** | それぞれのエントリで、独立に不要なコードを削れる。お客様用は gzip後 136KB（26KB減）。設定は、ビルドの対象を切り替える環境変数1つで済む |

## 決定

D を採用する。

- `scripts/build.mjs` が、スタッフ用（`dist/` を作り直す）→ お客様用（`dist/` に追加）の順に、Viteのビルドを2回行う。対象は、環境変数 `BUILD_TARGET` で切り替える（`vite.config.ts`）
- お客様用のビルドでは、`@firebase/auth`・`src/staff/`・`lib/firebase/staff.ts`・永続キャッシュのコードが含まれていたら、ビルドを失敗させる（`customerBundleGuard`）。リファクタリングなどで、うっかりスタッフ側のコードを読み込んだときに、CIで気づけるようにする
- 開発サーバー（`npm run dev`）は、1つのまま（両方のHTMLを配信する。開発中は、バンドルの大きさは問題にならない）

## 結果

- 良い点：お客様用が、スタッフ用の機能の増加に影響されない。お客様用の中身が、ビルドで検査される
- 悪い点：ビルドが2回になる（数百ミリ秒の増加）。Preact・Firestore SDK が、両方のバンドルに重複して入る（それぞれのページは、片方しか読み込まないため、問題にならない）
- 永続キャッシュの検査は、Firestore SDK の内部の文字列（`remoteDocuments`）に頼る。SDKの更新で、この名前が変わると、検査が素通りになり得る（逆に、誤ってビルドが失敗することはない）。SDKの大きな更新のときは、お客様用のバンドルの大きさを、あわせて確認する
- 見直す条件：Viteなどが、エントリごとに独立した tree-shaking を、1回のビルドでできるようになった場合
