# ADR-0003: 招待は、相手のGoogleメールアドレス宛てにする

- 状態: 採用（Accepted）
- 日付: 2026-10-03

## 背景

- イベントのメンバーを、招待で増やす（SPEC 3.4）。Cloud Functionsは使わない
- 招待リンクが、意図しない人に渡って、参加されることを避けたい

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A | リンクを持つ人なら、誰でも参加できる（ランダムなトークン、期限あり） | 実装は単純。ただし、リンクが転送されると、誰でも参加できる |
| B | 1回限りのリンク（1人が使うと無効） | 転送されても、最初の1人しか参加できない。ただし、最初の1人が意図した人とは限らない |
| **C** | **相手のGoogleメールアドレス宛ての招待（使い切り）** | 意図した人だけが参加できる。トークンの管理が不要で、ルールの条件も1つ増えるだけ |

## 決定

C案を採用する。

- オーナーが、相手のメールアドレス（小文字）をIDにした `invites/{email}` を作る。有効期限は作成の1日後
- 参加するときに、ルールが、`request.auth.token.email` と同じIDの招待が存在し、期限内であることを検証する（メールが検証済みであることも条件）
- 参加と同時に（同じバッチで）、その招待を削除する。これで、使い切りになる
- 招待リンクは、`/join?e={eventId}` のようにイベントIDだけを含む。秘密ではなく、守っているのは、メールアドレスの一致
- 取り消しは、オーナーが招待を削除する。再発行は、期限を延ばして作り直す

## 結果

- 良い点: 意図した人だけが参加できる。トークンの生成・管理が不要
- 悪い点・リスク: 相手のGoogleメールアドレスを、オーナーが知っている必要がある。Gmailの別名やWorkspaceのエイリアスでは、一致しないことがある（実機で確認し、分かる文言を出す）。招待にメールアドレスが保存される（読めるのはオーナーのみ。参加で削除される）
- 見直す条件: メールアドレスが分からない相手を招待したい要望が出た場合は、A案（リンクを持つ人は誰でも）も併用できるようにする
