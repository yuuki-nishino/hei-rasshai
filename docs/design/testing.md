# テスト計画

受け入れ条件は [SPEC.md](../SPEC.md) の8章。ここでは、**どう検証するか**を定める。

## 1. 方針

| 層 | ツール | 対象 | 自動化 |
|---|---|---|---|
| ドメイン（純粋関数） | Vitest | 日付・集計・レジ締め・パース・CSV・遷移・確定フローのreducer・接続状態・お客様画面の判定 | ○ |
| ルール | Firebase Emulator ＋ `@firebase/rules-unit-testing` | firestore.rules | ○ |
| データアクセス | Vitest ＋ Emulator（`test/data`、`npm run test:data`） | 確定フロー（冪等性・採番・墓標）、遷移、招待・参加、オフライン | ○ |
| 画面 | 手動（実機） | 画面の操作、オフライン、レイアウト | × |

- 画面のE2E自動化は、今回は見送る（実機での通し確認を重視。費用対効果が低いため）
- ルールの変更は、**必ず、ルールのテストを同時に追加する**
- ルールの検証項目（[security-rules.md](./security-rules.md) §5 のR1〜R11）は、下のルールのテストのケースに対応付ける（表の「R」の列）

### 5.2 通し確認（受け入れ条件に対応）
- [ ] 注文 → QR → お客様のスマホで開く → 完成 → 渡した、の表示が、数秒以内に変わる
- [ ] 機内モードで確定 → 確定されず、カートが残る
- [ ] 電波が弱い状態（低速・遅延）で確定 → 「送れていません」→ 再試行 → 二重にならない
- [ ] 「送れていません」の後、「やめる」→ 注文が現れない／登録されていれば成功扱い
- [ ] 確認中（unverifiable）に、次の注文を確定しようとすると、確定ボタンが無効
- [ ] 機内モードで「完成」「渡した」→ 復帰後に、お客様画面へ反映される。未送信の件数が、操作の数と合う
- [ ] 機内モードで「渡した」を押した後、再読み込み → 「未送信あり」が表示される
- [ ] 取り消し／戻す、支払い方法の変更（QRなしの、済みの注文を含む）が、売上・レジ締めに反映される
- [ ] 売上が、手計算と一致する。CSV・コピーが正しい
- [ ] オフラインで売上を開くと警告が出る。オフラインで、レジ締めが出来ない
- [ ] 招待 → 別のGoogleアカウントで参加 → 同じデータが見える。別のアカウントでは参加できない。参加後、同じ招待が使えない

## 6. CI
- GitHub Actions（`.github/workflows/ci.yml`）で、PRとmainへのpushのたびに、型・Lint・単体テスト・**ルールのテスト（Firestore Emulator）**・ビルドを実行する（#3。ルールの変更が、レビューで見落とされないように）
- `npm test` は、単体テスト（`npm run test:unit`）と、ルールのテスト（`npm run test:rules`。`firebase emulators:exec` で、Emulatorを起動して実行する）を、続けて実行する。ルールのテストには、Java 21 以上が必要
- データアクセスの結合テスト（§4）も、作ったら、同じようにCIで実行する
