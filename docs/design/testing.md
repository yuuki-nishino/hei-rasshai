# テスト計画

受け入れ条件は [SPEC.md](../SPEC.md) の8章。ここでは、**どう検証するか**を定める。

## 1. 方針

| 層 | ツール | 対象 | 自動化 |
|---|---|---|---|
| ドメイン（純粋関数） | Vitest | 日付・集計・レジ締め・パース・CSV・遷移 | ○ |
| ルール | Firebase Emulator ＋ `@firebase/rules-unit-testing` | firestore.rules | ○ |
| データアクセス | Vitest ＋ Emulator | 確定フロー（冪等性・採番）、遷移、招待・参加 | ○ |
| 画面 | 手動（実機） | 画面の操作、オフライン、レイアウト | × |

- 画面のE2E自動化は、今回は見送る（実機での通し確認を重視。費用対効果が低いため）
- ルールの変更は、**必ず、ルールのテストを同時に追加する**

## 2. ドメインのテスト（Vitest）

| 対象 | 主なケース |
|---|---|
| `toDay` | JSTの日付の境界（UTCの15:00前後）、端末のタイムゾーンが違っても同じ結果 |
| `summarize` | 取り消しの除外、現金とPayPayの分離、同じ品の複数注文の合算、価格変更時に別行になる、名前を変えても同じ行（`menuId`）、並び順 |
| `closingView` | 期待額、差額の符号、締め後の変更検知（追加・取り消し・支払い変更） |
| `parseBulkMenu` | 区切り（空白・カンマ・全角・コロン・タブ）、`円` 付き、全角数字、空行、エラー行（名前なし・価格なし・範囲外）、エラーがあれば追加しない |
| `buildCsv` | BOM・CRLF・引用符のエスケープ、`=` 始まりの無害化、取り消しの含有 |
| `canTransition` / 遷移で書く項目 | data-model.md §3 の全遷移、不正な遷移の拒否 |
| `calcChange` | 不足（負数）、ちょうど |

## 3. ルールのテスト（Emulator）

## 4. データアクセスの結合テスト（Emulator）

| # | ケース | 期待 |
|---|---|---|
| 1 | `confirmOrder` を、同じ `orderId` で2回呼ぶ | 注文は1件、番号は同じ、カウンターは1だけ進む |

### 5.2 通し確認（受け入れ条件に対応）
- [ ] 注文 → QR → お客様のスマホで開く → 完成 → 渡した、の表示が、数秒以内に変わる
- [ ] 機内モードで確定 → 確定されず、カートが残る
- [ ] 電波が弱い状態（低速・遅延）で確定 → 「送れていません」→ 再試行 → 二重にならない
- [ ] 「送れていません」の後、「やめる」→ 16秒の確認 → 注文が現れない／現れていれば成功扱い
- [ ] 機内モードで「完成」→ 復帰後に、お客様画面へ反映される
- [ ] 取り消し／戻す、支払い方法の変更が、売上・レジ締めに反映される
- [ ] 売上が、手計算と一致する。CSV・コピーが正しい
- [ ] 招待 → 別のGoogleアカウントで参加 → 同じデータが見える。別のアカウントでは参加できない
- [ ] 画面の見やすさ：屋外の明るさ、片手操作、ボタンの大きさ
- [ ] お客様画面：振動（Android）、色と文字の大きさ（iPhone）
- [ ] 接続状態の表示：オンライン／オフライン／未送信◯件の判定の遅れ
