# 毎度おおきに（maido-ookini）仕様書

イベントでの飲食物販売向けの、注文管理・呼び出し番号表示・売上集計Webアプリ。無料で運用でき、スマホ・タブレットのブラウザで動く。決済は行わない。

## 0. 名前と表記

屋台の掛け声から取った名前。画面の表示名と、システム上のIDを分けて使う。表記が揺れないよう、下の表のとおりに統一する。

| 用途 | 表記 |
|---|---|
| 正式名（ログイン画面の見出しなど） | 毎度おおきに |
| ホーム画面のアプリ名（PWAの `short_name`） | 毎度おおきに |
| PWAの `name` | 毎度おおきに |
| リポジトリ名・npmパッケージ名 | `maido-ookini` |
| Firebaseのプロジェクト名 | `maido-ookini`（IDは `maido-ookini-xxxxx` になる） |
| タグライン | イベントの注文管理、まいど、サクッと |

- ローマ字は `maido-ookini`（小文字・ハイフン）に統一する。`MaidoOokini` や `maido_ookini` は使わない
- npmの `maido-ookini` は空きを確認済み（2026-10-04）。Firebaseのプロジェクト名とホスティングのサブドメインは、作成時に確認する

### 画面の文言（接客の流れに合わせる）
| 場面 | 文言 |
|---|---|
| スタッフのログイン画面 | 毎度おおきに |
| お客様画面：調理中 | ただいま調理中です |
| お客様画面：できあがり | へい、お待ち！ |
| お客様画面：お渡し済み | 毎度おおきに！ |

## 1. 目的とスコープ

### 作るもの
| # | 機能 | 概要 |
|---|---|---|
| 1 | 注文管理 | 注文を入力して合計金額を表示。決済はしない。メニューごとの販売数と金額を記録する |
| 2 | 呼び出し番号とQR | 全注文に番号を振る。待ちが出る注文にはQRを発行し、お客様がスマホで読むと番号と状況が見られる |
| 3 | 調理ステータス | 店側の画面で「完成」「渡した」を操作すると、お客様のスマホに反映される |
| 4 | 売上集計 | 日別に、現金とPayPayを分けて売上を表示。メニュー別の数量・金額も出す |
| 5 | レジ締め | 現金の「あるはずの額」と「数えた額」の差額を確認・記録する |
| 6 | メニュー管理 | 素早く追加・編集・売り切れ切替・並べ替え・削除ができる |
| 7 | アカウントとイベント共有 | 個人のアカウントでイベントを作り、他のメンバーを招待して、共同で運営・確認できる |

### 作らないもの（スコープ外）
- 決済連携（PayPayやカードの処理）
- プッシュ通知
- スプレッドシート連携（CSV出力のみ対応）
- オフライン時の注文確定、端末ごとの採番
- 手書き運用に切り替えた分の後入力
- お客様画面の「あと◯組待ち」表示（将来拡張）
- 注文の品目・数量の、確定後の修正（取り消して入力し直す）
- 値引き・サービス・無料提供、現金とPayPay以外の支払い方法

## 2. 前提条件

- 会場の通信は、テザリングかキャリア回線。通信は基本あるが、途切れることがある
- **注文の確定には通信が必須**。通信できないときは確定させず、手書きか別端末に切り替える運用にする
- 運用費用は無料の範囲（Firebase Sparkプラン。Cloud Functionsなど有料機能は使わない）
- 想定規模は、1イベントあたり数百件／日。注文を取る端末は、基本1台
- 公開範囲は、当面は知人のみ。将来、一般に公開できるようにしておく（3.5）

## 3. アカウントとイベント

### 3.1 ログイン
- ログインは **Googleアカウント**のみ（パスワード管理が不要で、メールが検証済みのため）
- ログインには通信が必要。**当日までに、通信のある場所で済ませておく**。ログイン状態は端末に保持する

### 3.2 イベントとメンバー
- イベントを作ったアカウントが**オーナー**になる
- イベントのデータ（メニュー、注文、売上、レジ締め）は、**そのイベントのメンバーだけ**が読み書きできる。他のイベントのデータは見えない
- 1つのイベントに、複数のメンバーが参加できる。1人が複数のイベントに参加できる
- ログイン後は、自分が参加しているイベントの一覧から選ぶ

### 3.3 権限
| 操作 | オーナー | メンバー |
|---|---|---|
| 注文・調理・売上・レジ締め・メニュー・イベント設定の操作 | ○ | ○ |
| メンバーの招待・削除、招待リンクの再発行・無効化 | ○ | － |
| イベントの削除（注文などを含め、すべて削除） | ○ | － |
| イベントから抜ける | －（削除のみ） | ○ |

### 3.4 招待
- オーナーが、招待する相手の**Googleアカウントのメールアドレス**を入力すると、その人用の招待リンクができる。オーナーが、リンクを相手に送る（アプリからメールは送らない）
- **招待されたメールアドレスのGoogleアカウントでログインして**、リンクを開いた人だけが、メンバーになれる。別のアカウントでは参加できない（リンクが他の人に渡っても、参加されない）。参加できないときは、ログイン中のアカウントを示して、招待されていないことを知らせる
- 招待は、参加すると使い切りになる。有効期限は**1日**
- オーナーは、いつでも招待を取り消せ、同じ相手に**再発行**できる（期限が1日延びる）

### 3.5 イベント作成の制限
- 当面は**許可されたアカウントだけがイベントを作れる**。許可は、運営者がFirebaseコンソールで追加する（アプリの改修や再デプロイは不要）
- ログイン自体は、どのGoogleアカウントでもできる（事前登録は不要）。許可が必要なのは、イベントを**作る**ときだけ
- 許可のないアカウントでも、招待リンクを開けば、そのイベントのメンバーになれる
- 一般公開するときは、この制限を外す。公開前に、悪用対策（App Checkなど）を入れる

## 4. 注文のルール

### 4.1 番号
- 番号は、**全注文**に、**日別の連番**（1, 2, 3…）で振る。複数日開催でも、毎日1番から始まる
- 最大3桁を想定する。1000以上になっても、表示が崩れないようにする
- 「日」は、日本時間（Asia/Tokyo）の暦日とする。深夜営業の日またぎは想定しない

### 4.2 状態と遷移
状態は、`調理中`／`できあがり`／`お渡し済み`／`取り消し` の4つ。

| 操作 | 遷移 |
|---|---|
| 確定（QRあり） | → 調理中 |
| 確定（QRなし：その場で渡す） | → お渡し済み |
| 完成 | 調理中 → できあがり |
| 渡した | できあがり → お渡し済み |
| 調理中に戻す | できあがり → 調理中 |
| 渡したを戻す | お渡し済み → できあがり |
| 取り消し（確認あり） | 調理中／できあがり／お渡し済み → 取り消し |
| 取り消しを戻す | 取り消し → 取り消す前の状態 |

### 4.3 注文の保存と修正
- 注文は**削除しない**。取り消しは状態の変更で行う（イベントごと削除する場合を除く）
- 注文には、注文時点の品名と価格を書き写す。後でメニューを変えても、過去の売上は変わらない
- **品目・数量・合計・番号は、確定後に変更できない**。間違えたら、取り消して入力し直す
- **支払い方法とメモは、確定後に変更できる**（支払い方法：現金とPayPayの取り違えの訂正。メモ：書き間違い・追加の依頼〔「やっぱり辛さ抜き」〕の修正。空にもできる）。調理中・できあがりの注文は、調理画面から、いつでも変更できる。**お渡し済み・取り消しの注文は、当日分のみ**（調理画面の「済みも表示」から）。前日以前の済みの注文は変更できない。支払い方法の取り違えに気付いたら、レジ締めのメモに残す
- **メモ**（#40）：1注文に1つ。任意で、100文字まで（絵文字は2文字と数える）。「辛さ抜き」など、調理で気をつけることを書く。注文画面で入力し、確定後は、調理画面のカードから修正する。調理画面のカードで目立たせる。**お客様画面には出さない**。注文のデータは、注文IDを知っている人が読めるため、**個人の名前などは書かない**ことを、入力欄に添える。注文一覧のCSVに、列として含める
- 取り消しの理由は記録しない。お預り・お釣りも保存しない（確定時の画面上の計算のみ）

### 4.4 売上の定義
- 売上 ＝ 取り消し以外の注文の合計
- メニュー別の集計は、メニューと、注文時点の価格ごとにまとめる（途中で価格を変えても、過去分は変わらない）。品名は、まとめた中で最も新しい注文のものを表示する（途中で名前を直したときは、新しい名前に寄せる）

## 5. 注文確定の要件（最重要）

- 通信がなければ確定させない。**確定に失敗した注文は、存在しなかったことになる**
- 再試行しても、**二重登録にならない**
- 弱い電波で画面が固まらない。一定時間（8秒）で「送れていません」を出し、「もう一度試す」「やめる」を選べる
- 「送れていません」と出た後でも、実際には登録されている場合がある。**再試行の前と「やめる」の前に、登録の有無を確認し、登録されていれば成功として番号とQRを出す**
- 「やめる」を選んだ後に、遅れて注文が登録されてはいけない（見えない注文ができてはいけない）
- 登録の有無を確認できないとき（通信がない）は、その旨を表示し、通信が戻ったときに確認する
- 失敗の理由（オフライン、権限、タイムアウト）は、画面でメッセージを分ける

## 6. 画面仕様

### 共通
- タブレット・スマホ最優先。ボタンは44px以上。片手でタップしやすい配置
- **接続状態**は、問題があるときだけ、画面の上に出す（オンライン前提のアプリのため、ふだんは何も出さない）：通信が不安定なとき「通信状態が不安定です」、未送信があるとき「未送信◯件」（#19 で、常時表示から変更）
- 現在のイベントは、端末に保存して復元する。未設定なら「イベント」タブへ誘導する
- スタッフ用のタブ：注文／調理／売上／レジ締め／メニュー／イベント

### 6.1 注文
- メニューのボタンをタップで +1。ボタンには、数量バッジを付ける。売り切れは無効表示。調理なしの商品には、「調理なし」と添える
- カート：数量の増減、合計金額（大きく表示）、クリア
- 支払い方法：現金／PayPay（トグル）
- 現金のとき：お預り金額の入力と、「ちょうど／1000／5000／10000」のクイック入力。お釣り（不足）を表示
- メモ（任意。100文字まで。個人の名前などは書かない旨の注意つき。クリア・確定の成功で空になる）
- 「待ちあり：番号QRを発行する」のチェック。**初期値は、カートの中身から自動で決める**（#52）：調理が必要な商品が1つでもあればオン、調理が要らない商品（グッズなど）だけならオフ（その場で渡す）、空ならオン。手で変えられる。調理の要否が変わる操作（食べ物を足す・消すなど）をすると、また自動に戻る。前回の選択は記憶しない
- 確定ボタン（5章の要件）
- 確定後のモーダル：
  - QRあり：番号を大きく、QRコード、「閉じる」
  - QRなし：番号、合計、お釣り、「OK」

### 6.2 調理
- 2列：「調理中」「できあがり（受け渡し待ち）」。番号順
- 注文カード：番号（大）、明細（調理が要らない商品は、薄くして「調理なし」と添える。食べ物とグッズが混ざった注文は、調理画面に出し、作るものが目に入るようにする。#52）、**メモ（あれば、目立たせる）**、支払い方法、合計、経過分数
- 操作：「完成」「渡した」「調理中に戻す」「取り消し」（確認ダイアログあり）「QR（再表示）」「支払い方法の変更」「メモを足す・直す」
- **「完成」「渡した」は、押し間違いを直せる**：押すと、カードはすぐ次の状態に動いて見え、**5秒間「元に戻す」が出る**。この間は、サーバーに書かない（お客様の画面に、間違った状況が、一度も届かない）。戻さなければ、5秒後に書く。確認ダイアログは出さない（混んでいるときに、手が止まるため）。「調理中に戻す」「渡したを戻す」「取り消しを戻す」は、対象外（押し間違いは、もう一度押せば直せる）。5秒の根拠は、design/screens.md §3.5（#45）
- 「受け渡し済み・取り消しも表示」のトグル。表示中は、「渡したを戻す」「取り消しを戻す」も操作できる

### 6.3 売上
- 日付の切替。初期値は今日
- 現金／PayPay／合計（件数つき）
- メニュー別の表（単価、数量、小計）。小計の大きい順
- 「集計をコピー」（テキスト）、「注文一覧をCSV保存」（BOM付きUTF-8）
- 取り消し分は集計に入れない

### 6.4 レジ締め
- 日付ごとに：釣り銭の準備金（入力）、あるはずの現金（準備金＋現金売上）、数えた現金（入力）、差額（色分け：一致は緑、不一致は赤）
- 「締める」で記録する。何度でも上書きできる
- 締めた後に、現金売上が変わった場合（注文の追加、取り消し、支払い方法の変更）は、集計に反映し、「締め後に変更あり」を表示する。締めの記録は、上書きするまで変えない
- 準備金の初期値は、イベントに設定した値を使う。日別に変えられる

### 6.5 メニュー管理
- 一覧に、名前と価格のインライン編集（フォーカスが外れたときに保存）。価格は1円以上（無料・値引きは非対応のため、0円は不可）
- 売り切れの切替、**「調理あり／調理なし」の切替**（#52。標準は調理あり。グッズなど、調理せずに渡す商品は「調理なし」にする）、▲▼で並べ替え、削除（確認あり）
- 追加フォーム（名前、価格、「調理が必要」のチェック、Enterで追加）。まとめて追加は、すべて調理ありで入り、あとで商品ごとに切り替える
- まとめて追加：複数行のテキストを貼り付ける（1行に `名前 価格`。区切りは空白・カンマ・全角など）
- 「他のイベントからコピー」（任意・優先度低）

### 6.6 イベント
- イベントの作成（名前、開始日、終了日、釣り銭の準備金）。作成できるのは許可されたアカウントのみ（3.5）
- 自分が参加しているイベントの一覧と、切替。過去のイベントの売上も見られる
- メンバーの一覧、招待（相手のGoogleメールアドレスを入力して、リンクを発行）・再発行・取り消し、メンバーの削除（オーナーのみ）
- イベントから抜ける（メンバー）、イベントの削除（オーナー。確認あり、名前の入力で確定）

### 6.7 お客様画面
- ログイン不要。QRのリンクから、自分の注文1件だけが見られる
- 表示：番号（特大）、状況バッジ、状況に応じた案内文、明細と合計、最終更新時刻
- 状況と表示文言：
  - 調理中：バッジ「調理中」、案内「ただいま調理中です。できあがるまでこのままお待ちください」
  - できあがり：バッジ「へい、お待ち！」、案内「受け渡し口までお越しください」
  - お渡し済み：バッジ「お渡し済み」、案内「毎度おおきに！」
  - 取り消し：バッジ「取り消し」、案内「この注文は取り消されました。お近くのスタッフへお声がけください」
- 自動更新（店側の操作が、数秒以内に反映される。「完成」「渡した」は、押し間違いを直せる猶予（5秒）の分、遅れる）
- 「できあがり」に変わった瞬間に、端末が対応していれば振動する（iPhoneは非対応のため、色と大きな表示の変化で気付けるようにする。Chromeは、ページを一度でもタップしていないと振動できないため、振動は補助とする）
- 注文が見つからないとき、通信エラーのときは、それぞれ案内を出す
- 支払い方法・メモは表示しない
- 読み込みは最小限にする（弱い電波でも、すぐ開ける）

## 7. 非機能要件

### 7.1 セキュリティ
- 未ログインの人・メンバーでない人は、スタッフ用のデータ（注文一覧、売上、メニュー、レジ締め、メンバー）を読み書きできない
- お客様は、注文IDを知っている注文1件だけを読める。一覧は読めない
- **お客様に見える注文のデータに、スタッフのメールアドレスや名前を含めない**
- 品目・数量・合計・番号は、確定後に、誰も書き換えられない（支払い方法とメモは、メンバーが変更できる）
- 読み書きできるのは、**自分が参加しているイベント**のデータだけ。参加していない（招待されていない）イベントのデータは、他のイベントのメンバーであっても、読み書きできない

### 7.2 無料枠
- 無料枠（Spark）の範囲で運用できること。上限に達すると、全員が止まる（課金はされない）
- 想定規模（1イベント数百件／日）では、十分に収まる。見積もりと、画面ごとの読み込み方針は DESIGN.md に書く

### 7.3 オフラインとPWA
- **スタッフ用画面**：アプリ本体を端末にキャッシュし、通信がなくても画面は開ける。ホーム画面に追加できる（追加は任意。ブラウザのままでも、通信がなくても開ける）
- **お客様画面**：ホーム画面への追加やインストールは求めない。QRのリンクをブラウザで開くだけで使える。キャッシュなどの仕組みは使わず、毎回、最新を読み込む
- **注文の確定は、通信が必須**（5章）
- **ステータス変更（完成・渡した等）は、通信がなくても操作できる**。端末に溜まり、復帰後に自動で送られる。溜まっている間はお客様画面に反映されないため、接続状態の表示で気付けるようにする
- アプリの更新は、通信があるときに裏で行う。イベント当日の朝には更新しない運用とする

### 7.4 日付と表示
- 日付は日本時間で扱う。表示は日本語・円表記（`¥1,234`）

### 7.5 UI
- 屋外・立ち仕事で使うため、**大きな文字と大きなボタン**。コントラストを高く
- 状態の色：調理中＝黄、できあがり＝緑、お渡し済み＝グレー、取り消し＝赤、現金＝黄系、PayPay＝赤系
- お客様画面は、**番号の大きさ**を最優先にする
- 誤操作を防ぐ：取り消し・削除は確認ダイアログ、確定は大きなボタン
- キーボードフォーカスが見えること。`prefers-reduced-motion` を尊重する
- 雰囲気：屋台の明るさと、野外の自然な感じ（派手すぎない）。基調は赤系、ライト。見出し・ボタンは手書きの文字。アプリの呼び名は、イベント注文アプリ「毎度おおきに」（#29。詳細は design/visual.md）

### 7.6 動作確認の対象
- 直近2世代の iOS Safari・Android Chrome。実機（スマホ・タブレット）で通し確認する

## 8. 受け入れ条件（テスト項目）

### 機能
- [ ] メニューを追加・編集・並べ替え・売り切れ・削除できる。まとめて追加が動く
- [ ] 注文を確定すると、その日の連番が、全注文に振られる。日が変わると1番に戻る
- [ ] QRを読むと、お客様画面で番号と状況が見られる。状況は、店側の操作で数秒以内に変わる
- [ ] 4.2の遷移表のとおりに、状態を進めたり戻したりできる
- [ ] 取り消した注文は、売上に入らない。戻せば、取り消す前の状態に戻り、売上に入る
- [ ] 確定後に、支払い方法を変更でき、集計に反映される。品目・合計は変更できない
- [ ] 注文時にメモを残せる（100文字まで）。調理画面のカードに目立って表示され、確定後も修正できる（空にもできる）。お客様画面には出ない
- [ ] 現金・PayPayの別、メニュー別の数量・金額が、手計算と一致する
- [ ] レジ締めの差額が正しく出て、保存できる。締め後の変更で「締め後に変更あり」が出る
- [ ] イベントを作成でき、招待リンクで別のアカウントが参加でき、同じデータを見られる
- [ ] オーナーが、メンバーを削除でき、招待リンクを無効化・再発行できる。削除されたメンバーは、データを読めなくなる
- [ ] 期限切れ・取り消し済みの招待、または、招待されたのと別のGoogleアカウントでは、参加できない。参加すると、その招待は使えなくなる
- [ ] 許可されていないアカウントは、イベントを作れないが、招待されれば参加できる

### 失敗系
- [ ] オフラインで確定を押すと、確定されず、カートが残る
- [ ] タイムアウト後に再試行しても、注文が二重にならない
- [ ] タイムアウトしたがサーバー側で成功していた場合、番号とQRが出る
- [ ] 「やめる」を選んだ後に、注文が遅れて登録されない
- [ ] オフライン中に「完成」を押し、復帰後にお客様画面へ反映される
- [ ] 未ログイン・メンバーでないアカウントで、そのイベントのデータを読み書きできない
- [ ] お客様の権限では、注文一覧、売上、メニューを読めない
- [ ] お客様画面のデータに、スタッフのメールアドレス・名前が含まれない
- [ ] 確定後に、品目・合計・番号を書き換えられない（直接書き込みを試みても拒否される）

### セキュリティルールのテスト（Emulator）
- 未ログインの注文1件の取得は許可、一覧は拒否
- メンバーでないログインユーザーは、そのイベントのデータをすべて拒否
- メンバーは、そのイベントのデータを許可。ただし、注文の品目・合計・番号の変更は拒否。メモは、100文字まで・文字列のみ（作成時・変更時とも）
- オーナーだけが、メンバー管理・招待・イベント削除を許可
- 自分のメールアドレス宛ての、有効な招待がなければ、メンバーになれない（期限切れ・取り消し・別のアドレス宛ても拒否）

## 10. 決定事項と未確定事項

### 決定済み（2026-10-03）
| 項目 | 決定 |
|---|---|
| 端末 | 基本1台 |
| アカウント | 個人のGoogleアカウント。イベントごとのメンバー制（3章） |
| 招待 | 招待する人のGoogleメールアドレス宛て。有効期限1日、使い切り。オーナーが再発行・取り消しできる（[ADR-0003](./adr/0003-invite-by-email.md)） |
| 権限 | オーナーとメンバーの2段階。オーナーの譲渡は非対応。「閲覧のみ」は将来の拡張 |
| イベント作成 | 当面は許可制。将来、公開できるようにする（3.5） |
| 番号 | 全注文・日別連番・最大3桁（4.1） |
| 状態遷移 | 4.2の遷移表 |
| 確定後の修正 | 品目は不可、支払い方法のみ可（4.3）。理由は下記 |
| 準備金 | 日別のレジ締めを正とし、イベントの値を初期値にする |
| ホスティング | Firebase Hosting（無料枠で運用できる見込み） |
| UIライブラリ | Preact（[ADR-0001](./adr/0001-use-preact.md)） |
| 取り消し | 確認ダイアログのみ。理由は記録しない |
| お預り・お釣り | 保存しない |
| お客様画面の閲覧期間 | イベントが削除されるまで見られる。長期間残っても、読めるのは注文IDを知る人だけで、含まれるのは番号・品目・合計・状況のみのため、リスクは小さい |
| 支払い方法 | 現金とPayPayの2つに固定 |
| 値引き・無料提供 | 非対応 |

**確定後の修正を「品目は不可」とした理由**：修正を許すと、お客様が払った額と合計が食い違い、レジ締めが合わなくなりやすく、売上の履歴も追えない。不可にすれば、セキュリティルールで、品目・合計・番号の書き換えを拒否でき、堅牢になる。支払い方法は、合計が変わらず、現金・PayPayの内訳にだけ影響するため、変更を許す。
